## 1. 案件概要

### 1.1 背景

`in_out_log` から `HomeIotManager` への移行では、実行方式、設定管理、DBアクセス層、Webフレームワーク等を変更しました。一方、移行計画には既存機能・DB・処理ロジックを引き継ぐ方針が記載されています。

移行前後のコードを比較したところ、在宅・外出の遷移、入退室ログ、人感センサーWebhook、照明制御等に計画書で意図が確認できない差分が見つかりました。本案件では、非同期化やAPI構成を維持したまま、これらの判定結果を旧実装と一致させます。

### 1.2 目的

- `in_out_log` の判定条件、しきい値、履歴記録、家電制御の対象を回帰テストで固定する。
- `HomeIotManager` のサービス層を修正し、旧実装と異なる動作を解消する。
- 非同期実装・FastAPI・現在のWebhookパスおよびレスポンス形式は維持する。

### 1.3 対象外

- DBスキーマや既存テーブルデータの変更。
- 非同期クライアント、コンテナ、Quadlet、Jenkins等の実行・デプロイ構成変更。
- 旧実装に存在しなかった新機能の追加。
- Web UI の追加。

## 2. 修正項目

### 2.1 在宅・外出の状態遷移と帰宅処理

- 旧実装の `last_in`（最後に在宅を記録した時刻）と `out`（最後の帰宅時刻）の役割を維持し、各しきい値を同じ条件で適用する。
- `OUT_THRESHOLD_SECONDS` 経過後の帰宅判定は、在宅状態に変化したときに一度だけ実行する。
- 既存 `lasts` データを読み込んだ場合にも、過去の `out` 時刻からの経過時間だけを理由に、在宅中の帰宅処理を繰り返さない。
- `LAST_IN_THRESHOLD_SECONDS` による帰宅直後の猶予を復元する。帰宅時刻から猶予内のPing途絶は、旧実装同様に在宅時刻を更新する。

### 2.2 入退室ログと `lasts` の更新

- 旧実装の履歴仕様を維持する。帰宅確定時に、外出ログ (`value=0`) を直前の `last_in` の時刻で、帰宅ログ (`value=1`) を帰宅時刻で記録する。
- 外出しきい値を超えた時点では、旧実装になかった外出ログ行を追加しない。
- `lasts.out` は旧実装同様、帰宅時刻として更新する。
- 同一の帰宅遷移で履歴が重複記録されないことを保証する。

### 2.3 SwitchBot Webhook の判定

- 現行の `/switchbot/all`、クエリトークン、HTTPレスポンス形式は維持する。
- 旧実装同様、Webhookペイロードの `eventType`、`eventVersion`、`context` を検証し、不正なイベントは帰宅処理に渡さない。
- `WoPresence` かつ `DETECTED` の場合だけ人感センサーの帰宅候補とする。
- 旧実装同様、スマホPingが在宅を示す場合は人感センサーによる帰宅処理を行わない。
- 有効な帰宅候補でないWebhookを受け取ったとき、Webhookを契機に通常のPing在宅判定を実行して状態を更新しない。

### 2.4 Hue消灯判定

- Hue点灯状態の確認対象を旧実装と同じグループ2にする。
- 消灯指示の対象は旧実装と同じグループ3にする。
- `HUE_THRESHOLD_SECONDS` の起点と `hue_off` の更新条件を旧実装に合わせる。照明制御条件を `last_in` 起点へ置き換えない。
- Hueの状態が消灯を示す場合の `lasts.hue_off` 記録時機を旧実装に合わせる。

### 2.5 時刻境界

- 点灯時間の境界を旧実装に合わせる。旧条件は `hour >= HUE_ON_BEGIN_HOUR` または `hour <= HUE_ON_END_HOUR`。
- ルンバ稼働可能時間の境界を旧実装に合わせる。旧条件は `hour < ROOMY_SLEEP_START_HOUR` かつ `hour > ROOMY_SLEEP_END_HOUR`。
- デフォルト設定の6時台について、点灯とルンバ起動が旧実装と同じ判定になるテストを追加する。

### 2.6 IFTTT呼び出しとルンバ稼働記録

- IFTTT Maker Webhook のHTTPメソッドを旧実装に合わせて `GET` にする。非同期HTTPクライアントは維持する。
- ルンバ起動を試みたときの `lasts.roomy` 更新条件を旧実装に合わせ、通信結果を理由に再試行周期や多重起動の挙動を変えない。

## 3. 実装方針

1. 修正対象は原則として `homeiot/services/home_service.py`、`homeiot/web/webhook.py`、`homeiot/clients/switchbot.py`、`homeiot/clients/ifttt.py` と関連テストに限定する。
2. 同期化や旧モジュールの再導入は行わず、既存のasync/await構成に旧判定を移植する。
3. `in_out_log` の現行コードを参照元として、条件式・状態更新順序・記録時刻をケースごとに照合する。
4. 既存の公開API、環境変数、DBスキーマは変更しない。
5. 旧実装の副作用を再現する変更は、再現テストを追加してから実装する。テストで再現できない差分は、推測で仕様を追加せず、旧コード上の根拠を計画・PR説明に記載する。

## 4. テスト・検証計画

### 4.1 在宅・外出シナリオ

- 初回起動、在宅継続、しきい値未満の不在、外出確定、帰宅確定。
- 帰宅後180秒以内のPing途絶と、猶予経過後の不在。
- 旧 `lasts.in` / `lasts.out` を持つ状態で起動した場合。
- 同じ在宅状態を連続確認しても、帰宅シーケンス・ログが一度だけ実行されること。

### 4.2 履歴・照明・ルンバ

- 帰宅時の外出・帰宅ログの値と日時、および `lasts.out` の値。
- 外出しきい値到達時に外出ログを追加しないこと。
- Hue状態確認がグループ2、消灯指示がグループ3であること。
- `hue_off` 時刻を使った消灯判定と記録時機。
- 6時台・17時台・22時台の点灯／ルンバ起動境界。
- IFTTT失敗時を含む `lasts.roomy` 更新条件。

### 4.3 Webhook

- 有効な `WoPresence` / `DETECTED`、スマホ在宅時の検知。
- 未対応 `eventType` / `eventVersion`、`context` 欠落、不正JSON、他デバイス、未検知状態。
- 帰宅候補でないイベントが通常の在宅チェックを起動しないこと。
- 現行の認証とHTTPレスポンス形式が維持されること。

### 4.4 実行確認

- `tox -e unittest`
- `tox -e lint`
- 既存テストを含む全件が成功し、コアロジックの回帰テストが追加されていることを確認する。
